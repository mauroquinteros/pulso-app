# A Perfil reads only the Stocks it has movements in

[ADR 0011](0011-a-quote-is-read-apart-from-the-history.md) settled that the client reads `stocks` **unfiltered**, and it rejected filtering for a specific reason: the held tickers are derived from the **History**, so a filtered read would have to _wait_ for it, the two reads would become serial, and a failed History would cost the prices too. That reasoning still holds. This decision does not overturn it — it **removes its premise**. A `user_stocks` membership table, written by a trigger on the movement tables, lets Postgres do the filtering, so the read is still **one round trip that waits for nothing**.

A **Stock** does not change: it remains shared, never owned. `user_stocks` records which Stocks a **Perfil** needs _priced_, not which Stocks it possesses — the distinction that `CONTEXT.md` insists on and that `stores/perfil-scoped-state.ts` warns will rot if it is not said out loud.

## Considered Options

- **Leave the read unfiltered.** ADR 0011's decision, and zero work. Rejected on payload: the read ships every priced row in the table on every tabs mount and every foreground return. The table does not grow with users — `resolve-stock` only writes symbols Finnhub confirms on `exchange=US`, so it saturates against the US listing universe — but that ceiling is still an estimated ~475 KB at 5,000 tickers, against ~2 KB for a Perfil's own twenty. The figures are estimates from row width; nothing was measured.
- **A view over the movement tables.** Same payload, same single round trip, and nothing to write: membership would be _derived_, so it could not drift and a deleted movement would clean up after itself. Rejected in favour of the table for plan predictability — a composite primary key guarantees an index scan, where a view's plan is the planner's to choose — and because a table can carry columns that do not derive from movements. This is the option to reopen first if the trigger ever becomes a maintenance cost; the two produce the same rows.
- **Derive the ticker list in the client and pass an `in` filter.** Already rejected by ADR 0011, and still rejected, for its own reasons: it is the serialization this decision exists to avoid.
- **Keep `ticker` as the primary key of `stocks`.** The ticker is the identity of a **Stock** in the domain (`CONTEXT.md`), it is already single-spelled by the `ticker_is_uppercase` constraint, and at 1-10 ASCII characters it is _narrower_ than a `uuid`, not wider. Rejected by preference for a surrogate key, which is recorded here as exactly that — see the last consequence.

## Consequences

- **Membership is "ever traded", not "currently held".** A ticker sold in full keeps its row, because nothing removes a link — and the `sell` does not even fire the trigger, which is gated to `buy`. A sell can only follow a buy of the same ticker, whose link already exists, so firing would spend a scan of `stocks` to reach an `on conflict do nothing`; Postgres evaluates a trigger's `when` without calling the function, so it never enters plpgsql. That is deliberate: `CONTEXT.md`'s **Total Return of a stock** counts "every movement ever recorded for that ticker", and the backlog's _A fully exited position disappears from the app_ is the screen that will need those rows. Note that such a screen needs no **Quote** at all — with `shares` at 0 the price enters multiplied by zero — so what membership preserves for it is the Stock's `name`, not its price.
- **The trigger fires on INSERT only, and on a `buy` or a dividend.** There is no edit and no delete path in the app today — not one `.delete()` or `.update()` in `app/` or `lib/` — so a trigger for those would be handling what no code can produce. The DELETE and UPDATE policies on the movement tables _are_ live, so a direct PostgREST call could orphan a row; the cost of that is one Quote downloaded and unused, never a wrong figure. The edit screen brings its own trigger when it arrives.
- **A ticker missing from `stocks` is skipped in silence.** The trigger's `insert ... select` finds no row and inserts nothing. This is reachable from the app today — the dividend form accepts any non-empty string (backlog: _A dividend can be saved for a symbol nobody confirmed_) — so it is a normal path, not a theoretical one. Failing loudly instead was considered and rejected: a raised exception would abort the movement's own INSERT, turning a mistyped symbol into a save that fails with a generic database error, which is exactly the collapse ADR 0009 forbids between "the provider says no" and "we could not ask".
- **The RLS policy on `stocks` stays `using (true)`.** Scoping happens on `user_stocks`; RLS applies to both sides of the embed, so a membership-scoped policy on `stocks` would reintroduce per-row subquery work the table exists to avoid — and would break the join outright if it were written to exclude.
- **The read's shape changes; its contract does not.** `readStocks()` still returns `StocksAnswer` with a `Record<ticker, Stock>`, so the store, the engine, the hooks and every screen are untouched. What changes is inside `lib/stocks.ts`: the query becomes an embed on `user_stocks`, and rows arrive nested as `{ stocks: { ... } }`. The `!inner` is load-bearing — without it PostgREST nulls the embed instead of dropping the parent row, and the price filter stops filtering.
- **A confirmed Stock can now vanish before its movement is saved.** ADR 0013 puts a confirmed Stock straight into the store, and `answerRead` replaces the map wholesale. Confirm a symbol, background the app, return, then save: the read that fires on return no longer carries that Stock, because no movement references it yet, and the brand-new **Holding** reads "sin precio" until the next read. The unfiltered read did not have this window. Accepted rather than coded around — the cost is a missing price, not a wrong one, and it falls through the path that has always existed.

  **Resolved 2026-09-10.** Accepting it was wrong, and for a reason this entry did not see: the window is not only the background return described above. The read also fires on the tabs mounting, so a slow one answers _after_ a confirmation made seconds later — which is the ordinary case of opening the app and recording a buy, and is how it was finally reproduced. `answerRead` now merges the read's map over what is in hand instead of replacing it, so a read can no longer delete a Quote it was never able to carry. Merging keeps nothing it should not: a read omits a held ticker only if its link disappeared or its price went null, and neither is reachable — nothing deletes a link, and both writers skip rather than blank a price.

- **The migration must backfill.** `user_stocks` is born empty and the trigger only sees new inserts, so without a backfill every existing Perfil's portfolio goes unpriced on deploy. The backfill is a `distinct` union of both movement tables joined to `stocks` on ticker.
- **`refresh-stocks` is untouched, and ADR 0008's ceiling stands.** The cron still reads every row in `stocks`, because it must refresh any ticker any Perfil holds. At the current pacing a run costs roughly a second per Stock, so it stops finishing inside its ten-minute window at a few hundred tickers — long before the client read was ever a problem. This decision does not move that, and should not be mistaken for having done so.
- **`stocks.id` is a convention, not a technical requirement.** It is referenced by exactly one column in the whole system, `user_stocks.stock_id`: not by the movement tables, which keep `ticker` and are right to; not by the client, which never sees it; not by the two Edge Functions, which key on ticker; not by the `/stock/[ticker]` route. It was measured against the alternative and buys nothing — the collation gap that would have favoured it is closed by `ticker text collate "C"`, which is applied here anyway. It is recorded as a preference so that a future reader does not go looking for a technical reason that was never there.
